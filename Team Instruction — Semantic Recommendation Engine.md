## 1. Суть проекта

Мы создаём **локальную систему семантического поиска и рекомендаций**, которая не отправляет запросы во внешние API (OpenAI и т. п.), а сама понимает смысл текстов. Система:

1. берёт датасет (книги или товары с Kaggle: название, описание, жанр/категория, рейтинг);
2. превращает текстовые описания в числовые векторы (эмбеддинги) с помощью **SentenceTransformers**;
3. сохраняет векторы в векторном индексе **FAISS**;
4. принимает запрос на естественном языке (например, «Хочу что-то грустное про космос»), переводит его в вектор и за миллисекунды находит **топ-3 (или топ-K) самых близких по смыслу** объектов по косинусному сходству.

Это то, что на фрилансе продаётся как «умный поиск по тысячам товаров или документов компании».

### Что делает проект сильным (а не просто «учебным»)

- Мы не только строим поиск, но и **измеряем его качество** (Recall@K, MRR, время ответа).
- Мы **сравниваем подходы**: наивный поиск на NumPy (линейная алгебра вручную) против FAISS Flat и FAISS IVF.
- Мы показываем **математику**: векторы, матрицы, нормализация, косинусное сходство, скалярное произведение.
- Код написан по принципам **ООП**, покрыт тестами, оформлен как настоящий open-source репозиторий.
- Есть **технический отчёт** (5–8 страниц, английский язык) и **демо** (веб-интерфейс или Telegram-бот).

### Обязательный технологический стек

| Технология | Зачем используется |
| --- | --- |
| **ООП (Python classes)** | Архитектура: классы загрузчика, кодировщика, индекса, движка, оценщика |
| **Pandas** | Загрузка, очистка, объединение полей, хранение метаданных |
| **NumPy** | Матрицы эмбеддингов, нормализация, ручная реализация косинусного сходства (baseline) |
| **SentenceTransformers** | Модель эмбеддингов (напр. `all-MiniLM-L6-v2`; для русского/китайского — `paraphrase-multilingual-MiniLM-L12-v2`) |
| **FAISS** (`faiss-cpu`) | Быстрый векторный поиск (IndexFlatIP, затем IndexIVFFlat) |

Дополнительно (по желанию): Streamlit или python-telegram-bot (интерфейс), pytest (тесты), matplotlib (графики), Git/GitHub.

```
│   ├── index.py            # классы BaseIndex, NumpyIndex, FaissIndex
│   ├── engine.py           # класс RecommendationEngine
│   ├── evaluator.py        # класс Evaluator
│   └── app.py              # интерфейс (Streamlit / бот)
├── tests/
├── notebooks/              # EDA и эксперименты
└── docs/                   # отчёт, диаграммы, скриншоты
```

### Ключевые классы

- `DataLoader` — читает CSV через Pandas, проверяет колонки, удаляет дубликаты и пропуски.
- `TextPreprocessor` — собирает единое текстовое поле (title + description + genre), чистит текст.
- `EmbeddingEncoder` — оборачивает SentenceTransformer: `encode(texts) -> np.ndarray` (float32, нормализованные).
- `BaseIndex` (абстрактный класс, `abc.ABC`) — интерфейс: `build(vectors)`, `search(query_vec, k)`, `save(path)`, `load(path)`.
- `NumpyIndex(BaseIndex)` — baseline: скалярное произведение через `matrix @ query.T` и `np.argsort`.
- `FaissIndex(BaseIndex)` — `IndexFlatIP` (точный) и `IndexIVFFlat` (приближённый, быстрее на больших данных).
- `RecommendationEngine` — объединяет encoder + index + таблицу Pandas; метод `recommend(query: str, k: int = 3) -> pd.DataFrame`.
- `Evaluator` — считает Recall@K, MRR, среднее время ответа.

Обязательно использовать: **наследование** (BaseIndex → NumpyIndex/FaissIndex), **полиморфизм** (движок работает с любым индексом одинаково), **инкапсуляцию** (приватные поля, валидация входа), **type hints** и **docstrings** везде.

### Пример скелета (для согласования интерфейсов)

```python
from abc import ABC, abstractmethod
import numpy as np

class BaseIndex(ABC):
    @abstractmethod
    def build(self, vectors: np.ndarray) -> None: ...

    @abstractmethod
    def search(self, query: np.ndarray, k: int) -> tuple[np.ndarray, np.ndarray]:
        """Возвращает (scores, indices)."""
```

Нормализованные векторы + скалярное произведение = косинусное сходство. Это единое соглашение для всех индексов.

## 3. Роли в команде

У каждой роли есть **главный владелец** задач, но все обязаны читать код друг друга (code review).

### Роль 1 — Team Lead / Software Architect (ООП и интеграция)

**Зона ответственности:** архитектура, ООП-ядро, интеграция модулей, качество кода, управление проектом.

**Задачи:**

- Разработать структуру репозитория и базовые абстракции (`BaseIndex`, `RecommendationEngine`).
- Настроить GitHub: ветки (`main`, `dev`, `feature/*`), Pull Requests, Issues, GitHub Projects (доска задач).
- Проводить code review всех Pull Requests; следить за PEP 8, type hints, docstrings.
- Проводить еженедельные встречи, вести протоколы (кратко, в `docs/meetings/`).
- Собрать финальную версию, подготовить релиз v1.0 и презентацию проекта.

**Навыки, которые демонстрирует:** ООП, архитектура ПО, Git, лидерство, управление проектом. **Результаты (deliverables):** рабочая архитектура, `engine.py`, `index.py` (интерфейсы), настроенный репозиторий, финальный релиз.

### Роль 2 — Data Engineer (Pandas / NumPy, данные)

**Зона ответственности:** всё, что связано с данными до эмбеддингов.

**Задачи:**

- Выбрать и обосновать датасет (Kaggle: книги, фильмы или товары; минимум 5 000 записей).
- Провести EDA в Jupyter: распределения, пропуски, длины текстов, графики.
- Реализовать `DataLoader` и `TextPreprocessor` (Pandas): очистка, дубликаты, объединение полей, сохранение в `data/processed/`.
- Подготовить **тестовый набор запросов** (30–50 запросов с ожидаемыми релевантными объектами) для оценки качества.
- Написать unit-тесты для модулей данных.

**Навыки, которые демонстрирует:** Pandas, NumPy, EDA, работа с реальными данными, дисциплина в данных. **Результаты:** `data_loader.py`, `preprocessor.py`, ноутбук EDA, `data/processed/`, файл `eval_queries.csv`.

### Роль 3 — ML Engineer (SentenceTransformers и FAISS)

**Зона ответственности:** модель эмбеддингов и векторный поиск.

**Задачи:**

- Реализовать `EmbeddingEncoder` (SentenceTransformers): батчевое кодирование, нормализация, кэширование эмбеддингов в `.npy`.
- Реализовать `NumpyIndex` (baseline) и `FaissIndex` (Flat и IVF), сохранение/загрузка индекса.
- Сравнить минимум 2 модели эмбеддингов (напр. MiniLM и multilingual-версия).
- Провести бенчмарк: время поиска и память для NumPy vs FAISS Flat vs FAISS IVF при размерах 1k / 10k / 100k векторов (можно синтетически расширить).
- Объяснить в отчёте математику: размерность векторов, косинусное сходство, почему нормализация + inner product эквивалентны косинусу.

**Навыки, которые демонстрирует:** NLP, эмбеддинги, линейная алгебра, оптимизация, бенчмаркинг. **Результаты:** `encoder.py`, реализации индексов, таблица и графики бенчмарка.

### Роль 4 — Evaluation, Interface & Documentation Lead

**Зона ответственности:** измерение качества, интерфейс, документация и «упаковка» проекта.

**Задачи:**

- Реализовать `Evaluator`: Recall@1/3/10, MRR, среднее время ответа; построить графики (matplotlib).
- Создать интерфейс-демо: Streamlit-приложение или Telegram-бот (ввод запроса → топ-3 результата с описанием и оценкой сходства).
- Написать `README.md` (установка, запуск, примеры, скриншоты), диаграмму архитектуры.
- Написать **технический отчёт на английском** (Introduction, Method, Experiments, Results, Limitations, Conclusion).
- Записать 2–3-минутное демо-видео.

**Навыки, которые демонстрирует:** оценка моделей, продуктовое мышление, техническое письмо на английском, UX. **Результаты:** `evaluator.py`, `app.py`, README, отчёт PDF, видео-демо.

## 5. Командное соглашение

1. **Коммуникация.** Один основной чат (Telegram/WeChat) + еженедельная встреча 45–60 минут в фиксированное время. Ответ на сообщения по работе — в течение 24 часов.
2. **Задачи.** Всё ведётся через GitHub Issues и доску Projects. Никаких «устных» задач.
3. **Git-дисциплина.** Прямые коммиты в `main` запрещены. Работа в `feature/*`, слияние только через Pull Request с ревью минимум одного человека.
4. **Стиль кода.** PEP 8, type hints, docstrings, понятные имена; формат — `black`, проверка — `flake8`.
5. **Честная атрибуция.** В `CONTRIBUTORS.md` каждый пишет, что именно сделал лично. В заявке на поступление каждый указывает **только свой реальный вклад**. Приписывать себе чужую работу запрещено — это можно проверить по истории коммитов, а нечестность вредит заявке.
6. **Дедлайны.** Если задача задерживается, сообщить за 48 часов и попросить помощь. Скрывать проблему нельзя.
7. **Взаимопомощь.** Каждый обязан понимать весь проект на уровне «могу объяснить архитектуру на собеседовании». Раз в 2 недели — мини-обмен знаниями (15 минут).
8. **Принятие решений.** Решаем консенсусом; при споре — голосование, при равенстве решает Team Lead.
9. **Конфликты и неактивность.** Если участник не выходит на связь 7 дней — предупреждение; 14 дней — задачи перераспределяются, вклад фиксируется честно.
10. **Академическая честность.** Использование чужого кода и ИИ-помощников допускается только с указанием в README (раздел *Acknowledgements*). Датасеты и библиотеки указываются со ссылками и лицензиями.
11. **Уважение.** Критикуем код, а не людей. Ревью — конструктивное.

## 6. Критерии успеха проекта

- Работающий поиск: на тестовом наборе **Recall@3 ≥ 0.7** (цель; фиксируем фактический результат честно).
- FAISS быстрее NumPy-baseline на больших размерах, подтверждено графиком.
- Покрытие тестами ключевых модулей (цель ≥ 60%).
- Публичный репозиторий GitHub с README, лицензией и историей коммитов.
- Технический отчёт на английском + демо-видео.

## 7. Как использовать проект для поступления

Проект усиливает заявку, но **сам по себе поступление не гарантирует** — решают оценки, экзамены/языковые сертификаты, мотивационное письмо и требования конкретной программы. Чтобы проект работал на вас максимально:

- **Репозиторий GitHub** — ссылка в резюме и заявке.
- **Technical report** — приложить как PDF к портфолио.
- **Демо-видео** — 2–3 минуты, на английском.
- **Мотивационное письмо** — 1 абзац про проект: проблема → ваш вклад → результат с цифрами (напр. «FAISS ускорил поиск в N раз при Recall@3 = X»).
- **Рекомендательное письмо** — попросите школьного учителя информатики/математики или научного руководителя подтвердить ваш вклад.
- **Собеседование** — будьте готовы объяснить: что такое эмбеддинг, косинусное сходство, чем FAISS лучше полного перебора, почему ООП-архитектура.
- Проверьте на сайте университета (Zhejiang и др.) актуальные требования к бакалавриату для иностранных абитуриентов: сроки, языковой тест (HSK/IELTS/TOEFL), портфолио и т. д.
